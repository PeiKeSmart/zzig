## 2026-11-11 接收 Pek.ZCode 下沉的通用件

- **用户原话**：「同样的也是要尽可能的提取到zzig复用公共方法」
  （上下文：`G:\Code\Zig\Pek.ZCode` 基于 C# `DH.NCode` / Rust `Pek.RCode` 落地 Zig ORM 后，
  要求把与业务无关、可复用的能力提到 zzig，避免各仓库各写一份）。
- **检索证据（先查后写）**：zzig 内 `Decimal` / `DateTime` / `sqlite` 关键词**零命中**；
  `File` 仅有 `CurrentPath`/`CurrentPathZ`；无字符串缓冲类型。→ 不存在重复实现。
  `http` 模块已在用 `std.Io.Writer.Allocating` → `Buf` 用同一 API 不额外抬高版本门槛。
- **新增模块**（全部通用、零业务依赖）：

  | 模块 | 位置 | 对外名 |
  |---|---|---|
  | 字符串缓冲 | `src/text/buf.zig` | `zzig.Buf` |
  | 十进制（尾数+缩放因子） | `src/number/decimal.zig` | `zzig.Decimal` |
  | 日期时间（无时区，7 位小数秒文本） | `src/time/datetime.zig` | `zzig.DateTime` |
  | 数据库值模型 | `src/db/value.zig` | `zzig.db.Value` |
  | SQLite 驱动（动态加载 DLL） | `src/db/sqlite.zig` | `zzig.db.sqlite` / `zzig.sqlite` |
  | 文件工具（唯一临时名 / 静默删除） | `src/file/file.zig` | `zzig.File.UniqueTempName` / `DeleteQuiet` |

- **API 约定**：与仓库既有风格一致（`Strings`/`File` 用 PascalCase 函数名）；类型用名词（`Decimal`/`DateTime`/`Value`/`Buf`）。
  `zzig.db` 为分组命名空间，`zzig.sqlite` 是 `zzig.db.sqlite` 的便捷别名。
- **平台说明**：`zzig.sqlite` 用 Win32 `LoadLibraryA`/`GetProcAddress` 动态加载（Zig 0.17 的 `std.DynLib` 不支持 Windows），
  非 Windows 平台返回 `null`（驱动不可用）。`File.DeleteQuiet` 同理仅在 Windows 生效，其它平台静默跳过。
  两处均已在源码注释与 `docs` 中写明。
- **验证（实际输出）**：`zig build test --summary all` → `Build Summary: 5/5 steps succeeded; **51/51 tests passed**`
  （24 项主测试 + 27 项 XML 测试；本次新增 8 项：Decimal×2、DateTime×3、Buf×1、db.Value×1、sqlite 驱动×1、File×1）。
- **后续纪律**：这些能力**只在 zzig 修改**；消费方（首个是 `Pek.ZCode`）一律 import，不再复制实现。
  新增通用件的门槛：不依赖任何业务仓库、有独立单测、有清晰的生命周期/平台说明。

## 2026-11-12：Web MVC 一体化（Controller / 视图 / 区域 / wwwroot）

- **用户原话**：「zzig这个项目帮我参考C#和DH.RustBase实现web的Controller和视图以及区域还有wwwroot静态资源这一套方案」。
- **复用检索（先查后写）**：
  - `Get-ChildItem 'E:\Code\Rust\DH.RustBase\src\net'` → 命中 `router.rs`(15.8KB) / `controller.rs`(25.4KB) /
    `static_files.rs`(29.4KB) / `razor/*`(6252 行) 与 `Doc/{Razor子集模板引擎需求,SPA与MVC一体化}.md`；
  - 本仓库 `src/http/{http,server,enhanced}.zig` 只有「客户端 + 监听线程层」，无路由/控制器/视图/静态资源；
    `src/json` 是 jsmn 词法 + 按 key 查询（每次重新解析、不建值树）、`src/xml` 是 XML DOM —— 均无法承载视图模型树；
  - 结论：按 DH.RustBase 的职责划分在 `src/http/` 下新增 6 个模块，**API 面与语义对齐**，实现按 Zig 0.17.1 重写（无外部依赖）。
- **新增文件**：
  - `src/http/value.zig`：视图值模型（对象/列表/标量 + JSON 解析/序列化 + C# 口径文本化 + HTML 转义 + `ObjectBuilder`）；
  - `src/http/router.zig`：路由（`{name}` 段捕获、大小写不敏感、405+Allow、中间件洋葱链、fallback）+ 请求上下文 `Ctx`；
  - `src/http/controller.zig`：控制器（`/{prefix}/{action}`、动作名小写查表、参数绑定「路由→查询→表单→JSON」、
    `{code,message,data}` 信封、视图动作、1 参/2 参两种动作签名）；
  - `src/http/view.zig`：Razor 子集引擎（`@Model.X` / `@(expr)` / `@Raw` / `@if` / `@foreach` / `@{ var; Layout }` /
    `@RenderBody` / `@section` / `@RenderSection(Async)` / `@Html.Partial(Async)` / `@* *@` / `@@`；表达式子集含
    `??`/三元/比较/算术；子集外**编译期报错并带行列号**）+ 视图解析（`Views/{Controller}/{Action}.cshtml`、
    `Areas/{Area}/Views/...`、`Views/{Area}/...`、`Shared`、回退区域、显式 `/` 与相对片段）+ 布局链 + 分区 + 模板缓存；
  - `src/http/static_files.zig`：`wwwroot` 静态资源（MIME、默认文档、目录穿越防护、弱/强 ETag + 304、
    区域多根最长前缀优先、嵌入资源、SPA 回退 + 排除前缀）；
  - `src/http/web.zig`：`App` 装配（路由优先 → 静态兜底 → 404；区域注册 `addArea`；桥接 `http_server`）。
  - 示例 `examples/web_mvc_example.zig` + `examples/web/**`（Views / Areas / wwwroot），`zig build web-demo` 一键跑；
    文档 `docs/web_mvc.md`。
- **关键决策**：
  1. **控制器/中间件用「函数指针 + 上下文指针」**（Zig 无闭包捕获），以便跨线程共享且零分配；
     `Controller.map/get/...` 用 `comptime func: anytype` + `toActionFn` 同时支持 `fn(c)` 与 `fn(self, c)`；
  2. **静态资源挂路由之后**（与 DH.RustBase「StaticFiles 挂 fallback」一致），SPA 回退只在静态层且**只回退无扩展名路径**
     （避免缺失的 `.js/.css` 变成 HTML）；
  3. **视图缓存按「mtime + 长度」失效**，命中零读盘；旧模板只在 `ViewRenderer.deinit` 释放（不做引用计数，
     热改期短时可接受，已在文档标注）；
  4. **`server.Reply` 新增 `headers` 字段**：否则 `Location`/`ETag`/`Allow` 在桥接层被丢弃（302、304、405 就是坏的）；
  5. 文本化对齐 C#：`bool` → `True`/`False`、`null` → 空串、整数无小数；HTML 转义只处理 `& < > " '`
     （不追求 `HtmlEncoder.Default` 的全字符探测口径——那是 DH.RustBase 的 C# 互操作需求，本项目无此约束）。
- **踩坑与修正（实测）**：
  1. **编译期源码悬垂**：AST 里的文本/标识符切片指向源缓冲区，`loadTemplate` 编译后 `free(source)` → 渲染期读到垃圾
     （现象：`未定义的变量 UUUUU`）。修法：`compile()` 先把源码 `dupe` 进模板 arena，并在文档注明；
  2. **页面模型的栈悬垂**：动作里 `ofObject(&局部数组)` 返回后栈帧失效（现象：`<li></li><li></li><li>0.000…2</li>`）。
     结构性修法：新增 `value.ObjectBuilder`（字段名/数组复制进请求 arena），示例与文档统一改用它；
  3. Zig 0.17.1 API：`std.mem.trimLeft/trimRight` 已改名 `trimStart/trimEnd`；`std.Thread.Mutex` 已移除，
     改用 `std.Io.Mutex`（`lockUncancelable(io)` / `unlock(io)`）；`@typeInfo(Fn).params` → `param_types`；
     格式化字符串里的 `@{...}` 必须转义成 `@{{...}}`；union 字段类型不能直接写 `Node.render_section`（改用命名结构 `SectionCall`）；
  4. 模板里出现字面量 Razor 示例（如文档页面写 `@if`）必须写 `@@if`，否则被当代码解析（示例 About/Index 已修正）。
- **验证（实测）**：

    value 6 / router 6 / static 5 / view 10 / controller 4 / web 5 + 既有 value 用例）；

## 2026-11-13 增补：配置自愈 + 自动热加载 + 弹性线程池（Zig 0.17.1 原语）

- **用户原话**：「配置文件为什么没有注释的？」→「配置文件不是不存在时自动生成的吗？」→
  「如果配置项和实际的不一致以及没有注释等都要能自动补齐的吧」→「多余的键可以直接被清理掉」→
  「配置文件手改也要看不能自动加载到内存中使用」→「线程池是该用时用，不该用时不用吧」→
  「原语要用吧？」→「好像最近没有做每轮必提交推送以及决策和记忆等操作了」

### 一、配置自愈（缺键 / 无注释 / 多余键全部补齐）

1. `default_config_template` 改由**唯一布局** `config_template_layout` + `Config` 默认值**编译期渲染**。
   历史 bug：模板写死 `LogAsyncQueue = 8192`，而 `Config` 默认是 65536 —— 新生成的配置反而把队列改小了 8 倍。
2. `loadConfigFile` 加载时审计（`auditConfigText`）：缺键数 / 有无注释 / 多余键；
   命中任一 → 备份 `<路径>.old` → 用**实际生效值** + 完整注释原子重写；多余键按用户要求**直接清理**。
3. `reloadIfChanged` 走同一套自愈（外部改坏也会被修回）。
4. 新增测试：模板防漂移、自愈（缺键/无注释/多余键/值保留/备份存在）。

### 二、自动热加载（手改即生效）

- **根因**：`reloadIfChanged` **从未被任何内部代码调用**、`file_mutex` 声明了却从未使用 —— 手改配置永远不生效。
- `loadConfigFile` 成功后自动 `startAutoReload()`（默认 1000ms 检查一次，分片 100ms 睡眠保证退出快）；
  线程名设为 `T`，对齐 DH.NCore `TimerScheduler` 默认调度器的线程名（日志 `Name` 列 = `T`）。
- `shutdown()` 里**先停热加载线程、再关配置源**，两者无并发；新增 `reloadNow()`。
- `useFile`/`closeFile`/`emitText`/`emitBatch`/`fileEnabled` 全部走 `file_mutex`；
  sink 交换是「先建新的 → 锁内换指针 → 解锁后释放旧的」，杜绝 use-after-free。

### 三、踩坑（真 bug）

`loadConfigFile` 里 `errdefer file.deinit()` 与 catch 块中手写的 `file.deinit()` **重复释放** ——
配置解析/解码失败时直接段错误。已改为只由 `errdefer` 清理。

### 四、Zig 0.17.1 原语口径（实测确认）

- `std.Thread` 只剩 `spawn/join/detach/yield/getCurrentId/getCpuCount/setName/getName`；
  `Mutex/Condition/RwLock/Semaphore/WaitGroup` **全部迁到 `std.Io`**，且必须传 `io`。
- `std.Io.Condition.waitTimeout` 的 `Timeout.duration` 是 `Clock.Duration{ raw: Io.Duration, clock }`，
  不是 `{ .nanoseconds }`；相对时长用 `.awake`。
- `std.fmt.comptimePrint` **已移除**；编译期渲染要用 `bufPrint` + `break :blk s[0..s.len].*`（数组值拷贝）。

### 五、弹性线程池 `src/threading/pool.zig`

- 纯 `Io.Mutex` + `Io.Condition.waitTimeout` + `Io.Event`，**零轮询 / 零 sleep 循环**；
- 堆指针模型（`create`/`destroy`），worker 持有稳定地址；
- 弹性：`min_workers` / `max_workers` / `idle_timeout_ms`，扩容名额在锁内预留（多线程 submit 不冲破上限）；
- **该用则用**：短连接走池（实测线程创建+销毁 93.7us，占短连接 p50 293~334us 约 30%）；
  **不该用则不用**：长连接 / 流式订阅用独立线程 + `markAsLongTask()`（日志 `Kind=N` / `Name=L`，
  对齐 .NET `LongRunning` 不进池）；单线程 / 纯同步场景不用。

### 六、zgrpc 接入

`Server.dispatch`（`thread_per_conn` / `pool`）+ `Server.pool` + `Server.acceptLoop`；
`dispatchStream` 在池提交失败时**回退**为独立线程（队列满不丢连接）；bench 新增 `--pool` / `--pool-max`。

### 八、性能实测（Defender 已排除 Code 目录后，ReleaseFast，本机 16 核）

### 九、补充验证与加固（同日闭环「未验证」项）

- **线程池高并发压测（新增测试）**：8 个提交线程并发 `submit` 共 8000 个任务，
  `max_workers = 8`、队列 16384。结果：
  `提交=8000 / 执行=8000 / 队列满重试=0 / worker=8(上限 8) / 累计创建=8`。
  说明：任务不丢、worker 不越上限、**线程被真正复用**（累计只创建 8 个，没有反复 spawn）。
- **zgrpc `--pool` 前后对比（短连接，200 次 × 各 3 轮）**：

  | 模式 | QPS | p50 |
  |---|---|---|
  | 每连接一线程 | 1587 / 1236 / 1448（均 1424） | 329.7 / 381.6 / 346.1（均 352.5us） |
  | 弹性线程池 | 1796 / 2281 / 2148（均 2075） | 242.4 / 202.5 / 190.9（均 212.0us） |

  结论：QPS **+45.7%**，p50 **-39.9%**。

- **长连接（16 并发）不退化验证**：每连接一线程 23878 / 24903 QPS，
  弹性池 27928 / 24473 QPS —— 处于噪声区间，**无退化**。

### 一、p50 继续优化：去掉每连接的连接登记

- 定位：`serveConn` 每条连接都 `registerConn` → 一次自旋锁 + `append`（可能重分配）+
  断开时**线性扫描**移除。短连接下这是纯开销。
- 改法：`Server.track_conns` 默认 **false**；`spawnKeepalive()` 与 `pingAll()` **自动置 true**
  （默认走快路径，又不会因为忘配开关而让 keepalive 静默失效）。
- 实测（500 次 × 各 5 轮，同为池化）：
  - 强制登记：p50 中位 **221.6us**，QPS 均 1995
  - 默认不登记：p50 中位 **202.1us**，QPS 均 2194
  - → **p50 −8.8% / QPS +10%**（另一轮独立实验：−11.9% / +10.6%，方向一致）
- **首尾对比**（改造前「每连接一线程 + 登记」 vs 改造后「弹性池 + 不登记」，500 次 × 5 轮）：
  - p50 中位 **602.5 → 347.6us（−42.3%）**，QPS 均 **966 → 1431（+48.1%）**
  - 注：该轮机器负载偏高（同机同时段对比，比值有效）；低负载时对应数字为 235.5 → 202.1us。

### 二、p50 还剩多少空间（结论：headroom 有限）

- 复用连接下的 unary 往返 p50 ≈ **119us**（`bench` 单连接长连接模式，低负载时）。
- 短连接 p50 ≈ **202us**，故 `connect + h2 前言/SETTINGS 握手` ≈ **83us**。
- 也就是说剩余成本主要是**协议握手本身**，不是线程/调度开销。要再降需要减少握手往返
  （或客户端连接复用），属于协议层改造，不是参数调优。

### 三、TimerX / Cron 落地（新增）

- 新增 `src/threading/cron.zig`：**轻量级 Cron**（秒 分 时 日 月 周，支持 `a-b` / `a/b` / `a,b` / `#n` / `#Ln`），
  用**位图**存各字段（秒/分 u64，时 u32，日 u32，月 u16），命中判断 O(1)；
  `nextAfter` 按月/日/时/分**分层跳转**，不做逐秒扫描（C# 版是逐秒扫，年级表达式会扫 3000 万次）。
- `src/threading/timer.zig` 新增 `Scheduler` + `Timer`，对齐 `TimerX` 关键语义：
  - 周期（`due_ms` + `period_ms`）、一次性（`period_ms <= 0`）、绝对（墙上时钟对齐）、Cron（多表达式取最近）；
  - **不可重入**（`calling`）；`cost_ms` 滑动平均、`timers` 计数、`max_cost_ms` 超时告警；
  - 周期 < 10ms 直接 `error.PeriodTooSmall`（对齐 TimerX 防 CPU 占满）；
  - 周期调度用**开机滴答**（Windows `GetTickCount64` / 其它平台 `Io.Timestamp .awake`），免疫系统时间回拨；
  - 调度线程名 `T`（对齐 `TimerScheduler` 名为 Default 时的线程名）。
- **踩坑**：`std.Io.Condition.waitTimeout` **要求调用时持有互斥量**（内部先注册 waiter 再 unlock，
  返回前重新 lock）。我先 unlock 再调用 → `Mutex.unlock` 命中 `unreachable` → 测试进程 panic（exit code 3）。
- **踩坑**：Cron 位图必须按 `start` **归一化**（日/月 start=1，查询用 `值-1`），否则 `1 1` 永远不命中；
  另外 `a/b` 的上界应是**字段上界**而不是 `a+1`（C# 的 `max` 是字段上界）。
- 验证：zzig `zig build test` → **152/152**（新增 Cron 6 项 + 调度器 4 项）。
- **未对齐项（明确记录）**：弱引用回收（Zig 无 GC）、`Tracer` 链路追踪、多调度器分组、
  调度线程空闲 60s 自动销毁、`Async` 走线程池（当前回调在调度线程内联执行，与 `Async=false` 一致）。

## 2026-11-13 增补（三）：zgrpc 连接池（连接复用）

- **用户原话**：「连接复用 正常这个该有吧？」
- **现状核查**：`Caller` 有**单连接复用**（懒建 + 缓存 `*Conn`，出错 `dropConn` 重建），但
  **没有连接池**、且**不是线程安全的**（`conn` / `rr` / 计数器都是可变状态）——
  多线程共用一个 `Caller` 会直接数据竞争；每线程一个 `Caller` 又会让连接数失控。
  对比标准 gRPC 客户端（tonic `Channel`、grpc-go `ClientConn`）确实缺。
- **为什么不能只靠 h2 多路复用**：`client.Client` 是**同步阻塞**模型，内部持有 stream_id 序列与
  HPACK 动态表，同一条连接上无法并发发起多个 unary。所以**并发度 ≈ 连接数**，池是必需的。
- **实现**（`src/caller.zig` 新增 `Pool` / `PoolOptions`，`Conn` 改为 `pub`）：
  - `max_total`（总连接上限，含借出）、`max_idle`、`idle_timeout_ms`、`acquire_timeout_ms`；
  - `acquire()`：LIFO 空闲栈优先（顺手淘汰空闲超时的）→ 未达上限则**锁内预留名额**后到锁外建连
    （失败回滚名额，避免“假满”）→ 达上限则 `Condition.waitTimeout` 等归还；
  - `release(conn, healthy)`：不健康 / 池已关 / 空闲列表已满 → 直接关闭；否则入栈并唤醒等待者；
  - `unary()` 便捷法：借 → 调用 → 归还，连接级错误丢弃并发起退避重试（复用 `RetryPolicy` 与拦截器）。
- **验证**：
  - 单元测试：建连失败会回滚名额（`total` 归 0、`created` 为 0）；空地址 `error.NoEndpoints`；
    `deinit` 后 `error.PoolClosed`。zgrpc `zig build test` → **89/89**。
  - **端到端实测**（`bench --client-pool --conns 8 --iterations 500`）：
    `成功/失败 = 4000/0`，`总耗时 222.06ms，QPS 18013`，
    **`新建 8 次，复用 3992 次，丢弃 0 次；total=8 idle=8（max_total=8）`**
    —— 即 4000 次调用只用了 8 条连接，全部归还。
- 说明：借出中的连接在 `Pool.deinit()` 时不处理（由借出方 `release`）；这与连接池的常规契约一致。

### 补充：两个池叠加是不是「更大的提升」？—— 实测结论：**不是，收益不叠加**

- **用户原话**：「有连接池和线程池，性能是不是有个更大的提升？」
- 实测（8 线程 × 500 次 = 每组 4000 次调用，各 3 轮，同一时段）：

  | 组合 | QPS 三轮 | 均值 |
  |---|---|---|
  | 客户端池，1 线程 | 6290 / 5631 / 6867 | 6263 |
  | 客户端池，8 线程 | 18675 / 19096 / 19345 | 19039 |
  | 无池，8 线程各自独占连接 | 21288 / 21426 / 22446 | **21720** |
  | 仅服务端线程池，8 线程 | 20763 / 21939 / 21611 | 21438 |
  | 客户端池 + 服务端线程池 | 20481 / 23411 / 24222 | 22705 |

- **结论（长连接 / 已复用连接的场景）**：
  1. **客户端连接池反而更慢**（19039 vs 21720，**−12%**）：线程数固定且等于连接数时，
     池只是多了一层互斥 + 条件变量唤醒，没有减少任何建连成本；
  2. **服务端线程池在噪声内**（21438 vs 21720，−1.3%）：连接只建一次，线程创建成本早已摊薄；
  3. 「两者叠加」均值最高（22705），但三轮呈 **20481 → 23411 → 24222 单调上升**，
     更像机器预热，**不足以判定为真实提升**，不作为结论。
- **池真正有效的场景是短连接**，且两者各管一段、不叠加：
  - 服务端线程池省「每条连接一次线程创建」≈ 93.7us；
  - 客户端连接池省「每次 connect + h2 前言/SETTINGS 握手」≈ 84us；
  - 同一时段实测：短连接（每次新建）QPS 均 2194 → 连接复用（`--client-pool --conns 1`）**6263**，约 **2.9×**。
- **选型建议（写进 README 口径）**：
  - 长连接 / 流式 / 并发固定 → **都用默认**（每连接一线程、连接由调用方持有），别开池；
  - 高频短连接 → 服务端开 `dispatch = .pool`，客户端用 `Pool` 复用连接；
  - 池不是「越多越快」，它会引入同步开销：**并发度 ≈ 连接数**时，独占连接最快。

## 2026-11-13 增补（四）：性能与资源的后续优化路线（含成本/收益/风险）

- **用户原话**：「那要怎么继续优化提升性能及同时降低资源占用」
- **当前基线（实测，低负载时段）**：
  - 单连接复用 unary：**6459 QPS / p50 119us**；
  - 8 连接并发：**21720 QPS**（≈2.7k QPS/连接，**明显次线性**，说明有争用）；
  - 短连接：1431 QPS（p50 ~202us）；连接复用后 6263 QPS。
- **每连接资源占用（按代码核算）**：
  - 服务端：线程栈 **128 KiB**（`conn_stack_size`）+ 栈上收/发缓冲 **2 × 16 KiB** = **≈160 KiB/连接**；
  - 客户端：收/发缓冲 **2 × 16 KiB** 堆分配 = **32 KiB/连接**；
  - 512 连接 → 服务端虚拟内存 ≈ 80 MB，客户端堆 ≈ 16 MB。
- **已排除的方向（查证过，不是缺口）**：
  - HPACK 已使用 Huffman 编码（明文/Huffman 取更短者）；
  - 响应侧多帧写已由 `Stream.Writer` 的 16 KiB 缓冲合并，**不存在「每帧一次 syscall」**。
- **优化清单（按「收益/风险」排序）**：

  | 优先级 | 优化 | 预期收益 | 成本/风险 |
  |---|---|---|---|
  | P1 | **h2 多路复用**（一条连接跑多个并发流） | 连接/线程/缓冲数 ↓N 倍；单连接吞吐↑（实测 8 连接才 21.7k，说明单连接远未跑满） | **高**：需异步模型 + 客户端并发 API；`client.Client` 现在同步阻塞、持有 stream_id 序列与 HPACK 表 |
  | P1 | **HPACK 动态表索引编码**（当前只做静态表命中） | 重复响应头（`content-type`、`grpc-encoding`、trailers）从全文字节降到 1~2 字节索引，每请求少发 ~20~40 字节 | 中：需编码器状态 + 与对端 `SETTINGS_HEADER_TABLE_SIZE` 同步；解码侧已完整可对拍 |
  | P2 | **每连接缓冲按需**（小消息 4~8 KiB，大消息 16 KiB） | 客户端堆 **32 KiB → 8~16 KiB**（-50%~-75%） | 低：缓冲只是传输层读缓冲，h2 帧缓冲自管；大帧会多几次 read |
  | P2 | **服务端线程栈 128 → 64 KiB（可配）** | 服务端虚拟内存 **-50%** | 中低：需 512 连接压测确认不栈溢出（`serveConn` 有两块 16 KiB 栈数组，缩小缓冲后才安全） |
  | P3 | **IOCP / AFD 事件循环服务端** | 彻底去掉「每连接一线程」，线程数从 O(连接) 降到 O(核) | **很高**：要重写 accept/读循环；已有 `afd_reader.zig`（内核层读超时）可复用 |
  | P3 | 连接建立批处理（`SO_REUSEPORT` / accept 批量） | 短连接建连吞吐↑ | 中：平台差异大 |

- **结论**：**微调参数（缓冲大小、栈大小）只能省内存，提升不了多少性能**；要同时提升性能并降资源，
  必须走 **多路复用** 或 **事件循环** —— 两者都把「连接数/线程数」从与并发量线性相关，变成与并发量解耦。
- **建议顺序**：先做 P2 的缓冲按需（零风险、立刻省内存）→ 再做 HPACK 动态表（可对拍、收益确定）
  → 最后攻多路复用（大改造，需单独排期与压力测试）。

## 2026-11-13 增补（六）：TimerX 剩余项裁定 + Async / 多调度器 / Tracer 落地

- **用户原话**：「**仍未做**（已记入决策记录）：`Async` 回调走线程池、多调度器分组、调度线程空闲 60s 自动销毁、
  `Tracer` 追踪。这些还需要做么？另外要继续对比是否还有其他可以提升的。再怎么样用zig写的性能不能比其他语言性能和资源差吧。」

### 一、四项裁定

| 项 | 结论 | 理由 |
|---|---|---|
| `Async` 回调走线程池 | ✅ **已做** | 原来回调在调度线程内联执行，一个慢回调会阻塞**所有**定时器（TimerX 的 `Async` 正为此存在） |
| 多调度器分组 | ✅ **已做** | 按模块隔离：某组慢回调不与其他组的高频定时器抢同一条调度线程 |
| 空闲 60s 销毁调度线程 | ❌ **不做** | TimerX 是 GC 运行时下的"用完即回收"；Zig 有显式 `deinit`，进程内常驻才是正确语义，自动销毁只会带来"重建线程 / 丢定时器"的坑 |
| `Tracer` 链路追踪 | ✅ **已做**（钩子形式） | 提供 `begin/end` 两回调，可接自研打点 / OpenTelemetry；不做内置 tracer 实现（zzig 无 tracing 基础设施） |

### 二、实现要点

- **Async**：`Timer.async = true` + `Scheduler.setPool(pool)` → 回调提交到弹性线程池（`Kind=Y`）；
  池未绑定或队列满时**回退内联**，绝不丢这一轮触发。
  **生命周期约束**：池必须先于 `Scheduler` 销毁（否则池线程会访问已释放的 Scheduler）。
- **多调度器分组**：`Scheduler.startNamed(io, gpa, name)` / `zzig.threading.createScheduler(io, gpa, name)`
  同名复用；`get(name)` / `schedulerCount()` / `shutdownAll()`。
  线程名：`"Default"` → `T`（对齐 `TimerScheduler`），其它分组直接用分组名。
- **Tracer**：`Timer.tracer = .{ .ctx, .begin, .end }` + `tracer_name`；
  `runInline` 里 `begin → 回调 → end(elapsed_us)`。因 `TimerCallback` 返回 `void`，`failed` 恒为 false
  （要标错得由业务在回调内自行记录）。

### 三、这轮踩到的两个真 bug

1. **异步定时器只触发一次**：定时器 `calling=true` 时调度线程把它跳过，`wait_ms` 仍保持 60s，
   且异步回调完成后**没人唤醒**调度线程 → 睡满 60s。修法：`finishRun` 末尾 `Condition.signal`；
   同时"due 但 calling"时把 `wait_ms` 降到 1ms 兜底。
2. **耗时统计精度**：`cost_ms` 用开机滴答测量，Windows `GetTickCount64` 粒度约 **1~15.6ms**，
   短于一个滴答的回调会被计为 0ms。已在 `Timer.cost_ms` 文档写明：`max_cost_ms` 只适合粗粒度异常，不能当微基准。

### 三、结论（有数据支撑，不做超出范围的断言）

1. **低并发（c=1）zgrpc 明显更快**（+61%），且延迟低一个量级；
2. **单连接高并发（c=64）落后 21%** —— 这正好对应「同步 handler + 每连接一线程」：
   一条连接内的多个流是**串行**处理的，并发只能靠流水线，排队导致 p50 从 0.54ms 升到 3.43ms；
3. **多连接场景 zgrpc 反超**（+8%，p99 好 34%）—— 每连接一线程在这种形态下不是劣势；
4. **资源占用 zgrpc 低 6.5 倍**（4 MB vs 26 MB）：Go 有 GC 堆与运行时基线，Zig 是裸进程；
5. **语言本身没有劣势**：同样的 h2+gRPC 语义，我们在两种形态里的两种指标各有胜负，差距全部来自**并发模型**。

### 四、「事件循环 + 一连接多流」怎么落（分两步，风险可控）

- **服务端**：`h2.zig` **已经支持一连接多流**（有「两个流交错收头/收体、各自独立响应」的测试）。
  缺的是「流之间不互相阻塞」：现在 handler 同步执行，占着连接线程。要上事件循环需要
  把 accept/读/写改成 `std.Io` 异步 + 每条连接的帧处理做成状态机。**大改造**。
- **客户端**：真正的缺口在这里 —— `client.Client` 同步阻塞、内部持有 stream_id 序列与 HPACK 动态表，
  一条连接只能串行一个请求，所以「并发度 ≈ 连接数」。**要 1 连接 N 并发流，必须把 Client 改成
  「连接 actor + 请求队列 + 按 stream_id 回投」**。这是下一步性价比最高的一项。
- 顺序建议：**先客户端多路复用**（可直接用本次对拍验证：`--connections 1 -c 64` 应接近 grpc-go）
  → 再服务端事件循环。

## 2026-11-12 增补：静态资源预压缩（.gz 优先）—— 与 DH.RustBase 口径差异说明

- **用户原话**：「DH.RustBase和zzig是否也有实现web的压缩功能？」。
- **实测结论**：
  - **DH.RustBase 有**响应级 gzip（`src/net/http.rs:1085 finalize_http_response`）：默认开、`gzip_min_size=256`、
    类型白名单 `is_compressible_type`、加 `Vary: Accept-Encoding`、压完不比原body小就放弃；
    但**静态文件明确不压**（`if resp.file.is_some() { return resp }`，注释「压缩需要整读，会把内存省下的又吐回去」）。
  - **zzig 原本没有**服务端压缩：`src/http/http.zig:29-35` 只有**客户端解压**（`isGzipMagic` / `gzipDecompressAlloc`），
    `static_files.zig` / `web.zig` / `server.zig` 全量搜 `gzip|Content-Encoding` 零命中。
- **本轮实现（磁盘根预压缩）**：
  1. `serveRequest` 读 `Accept-Encoding`（大小写不敏感）→ `serveInternal(..., accept_gzip)`；
  2. `serveDisk` → `diskWithPrecompressed`：先试 `rel + ".gz"`，命中则下发该文件；
  3. `diskResponse` 新增 `DiskOpts{ file_rel, extra_headers }`：**打开 `.gz`，但 Content-Type 按原始路径推断**；
  4. 响应头加 `content-encoding: gzip` + `vary: accept-encoding`；
  5. `buildResponse`/`buildStaticHeaders` 增加 `extra` 头参数；**`serve` 旧签名保留**（内部传 `false`），既有测试不受影响。
- **为什么选预压缩而不是运行时压缩**：zzig 静态资源已全流式（`stream_threshold = 0`），运行时 gzip 必须整读，
  等于把上一轮省下的内存又吐回去；预压缩是「构建期压一次、运行时原样流式」，零 CPU。
- **验证**：`zig build test` → **143/143**（新增用例覆盖三种路径：带 gzip 下发 `.gz` + 头齐全、
  不带 gzip 回退原文件且无编码头、无同名 `.gz` 时回退不报错；并断言 Content-Type 仍为 `text/javascript`）。
  **真机未跑**（现有示例 `spa_demo` 用编译期嵌入资源、无磁盘根；`web_mvc_example` 未安装到 zig-out），如实记录。
- **未做（重要）**：`embedAssets`（单 exe 形态）**不支持 `.gz` 变体** —— 需要 `spa_gen` 构建期生成 gzip
  并给 `Embedded` 加 gzip 字段；已写入 `docs/spa_vue.md` 第 7 节。动态响应 gzip 也未做。
