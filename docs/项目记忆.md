## web-mvc.md

# zzig Web MVC（2026-11-12 新增）

- 入口：`zzig.web`（`src/http/{value,router,controller,view,static_files,web}.zig`）；文档 `docs/web_mvc.md`；示例 `zig build web-demo`（`examples/web/**`）。
- 约定：`Views/{Controller}/{Action}.cshtml`、`Areas/{Area}/Views/...`、`wwwroot` / `Areas/{Area}/wwwroot`（URL 前缀 = 区域名小写）。
- 处理顺序：路由优先 → 静态资源兜底 → 404；SPA 回退只对「无扩展名」路径生效。
- 视图模型必须用 `value.ObjectBuilder.init(c.arena)`（字段名/数组复制进 arena）；`ofObject(&局部数组)` 会悬垂。
- 组件式调用：`@await Component.InvokeAsync("Name", 参数)` / `@Component("Name", 参数)`；注册 `app.registerComponent`；
  视图约定 `Views/Shared/Components/{Name}/Default.cshtml`（区域内优先 `Areas/{Area}/Views/Shared/Components/...`）。
- 静态资源：`Options.wwwroot` 可改默认目录；`Options.static_roots` / `app.addStaticRoot(prefix, dir)` 加额外根
  （绝对路径可用，最长前缀优先，每根可覆盖 max_bytes/stream_threshold/cache_control）。
- 磁盘静态文件**默认全流式**（`stream_threshold = 0`）：每请求恒定 40 KB 缓冲，不整读；
  Linux 走 `Writer.sendFile`（内核 sendfile 零拷贝），Windows 回退 32 KB 读-写循环。
  想让小文件一次 read 可把阈值调高（如 64 KB）。
- 扩展名策略（对齐 ASP.NET `ServeUnknownFileTypes=false`）：未知扩展名/无扩展名默认 404；
  `statics.setMimeType(ext, ct)` 只放开指定格式，`serveUnknownFileTypes(true)` 全放开，
  `RootOptions.serve_unknown_types` 按根覆盖（下载目录放开、主站严格）。嵌入资源不受限。
- 大文件走 `Response.file` → `server.Reply.file` → `respondStreaming`；**HEAD 分支只能 `bw.flush()`，
  绝不能 `end()`**（eliding 不递减 content-length，会命中 `assert(len == 0)` panic）。
- `view.compile()` 会把源码复制进模板 arena（AST 持切片）；模板缓存按 mtime+长度失效，旧模板到 deinit 才释放。
- 测试须登记到 `src/zzig.zig` 末尾 `test { _ = @import("http/...zig"); }`，否则 `zig build test` 不收集。
- Zig 0.17.1：`trimStart/trimEnd`、`std.Io.Mutex`（配 `self.io`）、`@typeInfo(fn).param_types`。

# zgrpc 服务反射（2026-11-13 实现）

- 三层：`src/proto.zig`（proto3 子集解析）→ `src/descriptor.zig`（→ FileDescriptorProto）→ `src/reflection.zig`（ServerReflectionInfo 双向流）。
- 路由：`refl.streamRoute()` / `streamRouteV1Alpha()`，走 **per-route `ctx`**（`route.ctx orelse server.outer_ctx`），不抢业务 ctx。

## 0.17.1 同步原语（实测确认，2026-11-13）
- `std.Thread` **只剩**：`spawn/join/detach/yield/getCurrentId/getCpuCount/setName/getName`。
- `std.Thread.Mutex` / `Condition` / `RwLock` / `Semaphore` / `WaitGroup` **全部删除**，迁移到 `std.Io.Mutex` / `std.Io.Condition`。
- `std.Io.Mutex` 可独立用（`mutex: std.Io.Mutex = .init`），`lock/unlock` 不传 io。
- `std.Io.Condition.wait/waitTimeout` **必须传 `io` 且返回 cancelable 错误联合**；没有 `std.Thread.Condition` 那种无 io 版本。
- 测试里拿 io：`std.testing.io`；跨线程全局：`std.Io.Threaded.global_single_threaded.io()`。
- 结论：需要阻塞式等待的池/队列，要么传 `Io`（API 带 io 参数），要么用原子 + `compat.sleep` 轮询。
- **坑（必记）**：`std.Io.Condition.wait/waitTimeout` **要求调用时持有该 `Io.Mutex`**——内部先注册 waiter 再 `unlock`，返回前重新 `lock`。先 unlock 再调用 → `Mutex.unlock` 命中 `unreachable` → 进程 exit code 3。
- `std.Io.Event`：`set(e, io)` / `reset(e)`（无 io，且要求无 pending wait）/ `waitUncancelable(e, io)` / `waitTimeout(e, io, timeout)`。
- `std.fmt.comptimePrint` 在 0.17.1 **已不存在**；编译期渲染用 `std.fmt.bufPrint` + `break :blk s[0..s.len].*`（数组值拷贝，不能直接返回切片：会报 "global variable contains reference to comptime var"）。
- 同步测试里要真睡眠：`compat.sleep(ns)`（Windows 走 `NtDelayExecution`）。

## 事件循环（2026-11-13 实测）
- **zio 就是事件驱动的**：`src/ev/` 是 libuv 风格回调循环，后端 Windows→**IOCP**、Linux→io_uring(退 epoll)、
  macOS/BSD→kqueue、其它→poll。`src/io.zig` 是 **`std.Io` 的实现**（"backed by zio's runtime"）。
- 所以 **zgrpc 零改动即可跑事件循环**：把 `std.Io` 从 `std.Io.Threaded` 换成 `zio.Runtime.io()`。
  现成示例 `zgrpc/examples/with-zio/`；本轮给它加了 `serve <port>` 模式以便用同一客户端对拍。
- 同客户端实测（conns 1..512）：事件循环吞吐与「每连接一线程」**持平**（个别档反而低 11%~21%）。
  原因：每请求仍是 1 读+1 写，瓶颈不在线程调度；外加 std.Io vtable 间接 + IOCP 完成队列往返。
- **真正的收益是资源**：300 连接保持期间 线程 303 → **21**（14x），RSS 57MB → 52MB（持平，
  因为线程栈惰性提交本来就小）。
- 结论：要吞吐用线程模型 + 批量写；要连接规模用 zio 后端。同一份代码，两种 `std.Io` 取舍。

## 连接规模的墙（2026-11-13 实测，ghz 持长连接 12s）

  事件循环 21 线程、零拒连。

  已加 `Server.default_backlog = 1024`。提到 1024 后 2000 连接零拒连。
- 已修的三个静默缺陷：① `acceptLoop` 的 `catch return` 会整体退出（改记日志+退避）；
  ② 建线程失败静默关连接（改明确告警）；③ backlog 默认太小。

## 事件循环一等化 + 万连接（2026-11-13，zgrpc `7e7be45`）
- `ConnDispatch.task` 是一等调度：连接跑在 `std.Io.Group` 任务里，`acceptLoop` 退出时 await 任务组。
  任务创建失败自动回退独立线程。默认仍是 `thread_per_conn`。
- **10000 条长连接实测**（同机 ghz 15s）：zgrpc(.task+zio/IOCP) **55213 QPS / 24 线程 / 零拒连**；
  grpc-go 33750 QPS → **zgrpc +64%**。
- **内存关键**：zio `stack_pool.committed_size` 默认 **256 KiB/协程** → 1 万协程 2.5 GB。
  改 `committed_size = 16 KiB` + `maximum_size = 1 MiB` 后 10k 连接 RSS **1215 MB → ~750-850 MB**。
  再配合 `conn_recv_buf_size`/`conn_send_buf_size` = 4 KiB/4 KiB（每连接仅 8 KiB）。
  剩余约 75 KB/连接，主要是 zio 任务/栈 + 内核 socket 缓冲。
- zio 服务端启动模板（示例 `examples/with-zio/main.zig`）：
  `Runtime.init(gpa, .{ .executors = .auto, .stack_pool = .{ .maximum_size = 64KiB, .committed_size = 4KiB } })`
  + `dispatch = .task` + `addr.listen(io, .{ .reuse_address = true, .kernel_backlog = Server.default_backlog })`。
- 回归测试：真实 socket 验证 `.task` 调度（connCount 0→1→0），轮询上限 1 秒避免挂死测试。
  注意 `std.Io.net` 没有 getsockname，测试只能试几个高位端口。

## 万连接内存调优（2026-11-13，zgrpc 示例默认值）
- **Windows 上真正决定每连接内存的是 zio `stack_pool.maximum_size`（保留上限），不是 `committed_size`。**
  实测 5000 连接（committed 4 KiB 固定）：max 1MiB/256KiB/128KiB 都是 ~612MB（122KB/连接）；
  **max 64 KiB → 92 MB（18KB/连接）**。只改 committed_size 无效（Windows 走 RtlCreateUserStack，非 slab）。
- 最终配置：`stack_pool = .{ .maximum_size = 64KiB, .committed_size = 4KiB }` +
  `conn_recv_buf_size/conn_send_buf_size = 4KiB`。
- **10000 连接：峰值 RSS 132 MB（原 1215 MB，↓9.2×）/ 7607 句柄 / 45800 QPS / 零拒连**；
  同条件 grpc-go 33750 QPS → +36%。
- 测量方法：`Start-Job` 每秒采样 `WorkingSet64`/`HandleCount`，前台跑 ghz 固定时长，最后 `Receive-Job`。
  这比"跑完再采样"可靠（连接关闭后 RSS/线程都会回落）。
- `maximum_size = 64 KiB` 约束用户 handler 的栈用量（库自身只用几 KB）。

## Cron / Timer（2026-11-13 新增）
- `zzig.threading.cron.Cron`：位图存字段（秒/分 u64、时 u32、日 u32、月 u16），`nextAfter` 分层跳转不逐秒扫。
- 位图必须按 `start` 归一（日/月 start=1 → 存 `值-1`）；`a/b` 的上界是字段上界而非 `a+1`。
- `zzig.threading.timer`：`Scheduler.start(io,gpa)` / `add(&timer)` / `remove` / `deinit`；`Timer.period/absolute/cron`。
- 语义：不可重入、<10ms 拒绝、开机滴答防时间回拨、调度线程名 `T`、cost/timers/max_cost_ms。
- 未对齐：Async 走池、多调度器分组、空闲 60s 销毁调度线程、Tracer。
